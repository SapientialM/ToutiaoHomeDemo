## 2. 方案调研

### 2.1 整体技术方案

针对课题"开发一个高度还原今日头条首页的 Android Demo"这一需求，整体技术方案需要解决以下关键问题：

1. UI 渲染：XML + RecyclerView（传统方案）还是 Jetpack Compose（现代方案）？
2. 架构模式：MVC / MVP / MVVM / MVI 哪个适合信息流场景？
3. 分页：手动分页（传统方案）还是 Paging3（Google 官方方案）？
4. 数据源：抓真实接口（受版权 / 限流限制）还是 Mock（合成数据）？
5. 数据缓存：内存缓存（最简）还是 Room 持久化（离线可用）？

### 2.2 候选方案对比

**方案 A：XML + RecyclerView + MVP（传统方案）**

| 维度 | 表现 |
|------|------|
| 上手成本 | 低（多数 Android 开发者熟悉） |
| UI 性能 | 良好（RecyclerView 优化成熟） |
| 状态管理 | 弱（View 层与 Presenter 双向通信） |
| 与字节栈匹配度 | 中（字节新需求主推 Compose） |
| 复杂状态管理 | 弱（多状态切换容易混乱） |
| 课题加分项 | 不突出（传统栈，非加分点） |

**方案 B：Jetpack Compose + MVI + Clean Architecture（现代方案，本项目采用）**

| 维度 | 表现 |
|------|------|
| 上手成本 | 中（需要学习 Compose 思维） |
| UI 性能 | 良好（Compose 1.6+ 性能已对标 RecyclerView） |
| 状态管理 | 强（StateFlow + 单一 State 集中管理） |
| 与字节栈匹配度 | 高（字节新需求主推 Compose） |
| 复杂状态管理 | 强（频道 / 筛选 / 分页 / 刷新都可塞进单一 UiState） |
| 课题加分项 | 强（课题要求 Compose + MVI） |

**方案 C：Flutter / RN（跨端方案）**

| 维度 | 表现 |
|------|------|
| 上手成本 | 高（需要学习 Dart / JS） |
| 性能 | 中（与原生有差距，复杂信息流可能掉帧） |
| 与课题匹配度 | 低（课题考察的是 Android 原生开发） |
| 评委接受度 | 低（与字节客户端栈不一致） |

**最终选型**：方案 B（Jetpack Compose + MVI + Clean Architecture）。原因：

1. **完全覆盖课题加分项**：Compose + MVI 直接对应加分点描述
2. **与字节栈一致**：字节内部新需求主推 Compose，技术栈匹配
3. **信息流场景天然契合**：单一 UiState 集中管理多状态（频道 / 分页 / 刷新 / 错误）
4. **工程化优势**：单向数据流使 bug 容易定位，状态变化可追溯

### 2.3 数据源方案

**方案 A：抓真实接口（抓包头条 App）**
- 优点：数据真实
- 缺点：① 版权风险 ② 接口会变 ③ Key 申请麻烦 ④ 网络依赖大

**方案 B：开源新闻 API 聚合**
- 优点：合规
- 缺点：① 数据非头条真实数据 ② 多数 API 限流 ③ 字段与头条不一致

**方案 C：AI 合成 Mock 数据（最终采用）**
- 优点：① 完全脱机可跑 ② 字段可任意控制 ③ 数量自由 ④ 零真实信息
- 缺点：① 数据非真实头条 ② 需要做一定工程化（合成 + 分页 + 多频道）

**最终选型**：方案 C。课题 Q&A 明确回答"首页数据如何获取"包含"AI mock"选项，AI Mock 完全合规且工程化价值高。

### 2.4 分页与缓存方案

**方案 A：手动分页 + 内存缓存**
- 优点：简单
- 缺点：① 离线不可用 ② 重复造轮子 ③ 与 Google 官方方案脱节

**方案 B：Paging3 + RemoteMediator + Room（最终采用）**
- 优点：① 官方推荐 ② 离线天然支持 ③ 与 Room 集成完善 ④ 社区生态成熟
- 缺点：① 学习成本 ② 配置较复杂

**最终选型**：方案 B。完美匹配课题"进阶功能"中的"下拉刷新 + 加载更多 + 数据库存储"三项。

## 3. 技术方案

### 3.1 原理阐述

#### 3.1.1 MVI 单向数据流

**原理**：MVI（Model-View-Intent）是一种单向数据流架构模式，所有用户操作都被建模为 `Intent`（在本项目中为 `UiEvent`），通过 ViewModel 转换为 `State`，UI 只负责渲染 State 与发送 Event。

**为什么适合信息流场景**：
- 复杂状态（频道 / 筛选 / 分页 / 刷新 / 错误）天然适合用单一 `UiState` 集中管理
- 单向数据流使 bug 易于追踪（"状态变了" → 直接看 State 怎么变）
- 配合 Compose 的 `collectAsStateWithLifecycle`，重组范围精确可控

**数据流向**：

```
用户操作 → UiEvent (Sealed) → ViewModel.onEvent()
                                   ↓ 业务编排
                       UiState (StateFlow) ← Repository
                                   ↓
                Screen collectAsStateWithLifecycle
                                   ↓
                          Compose 重组（@Immutable）
                                   ↓
                              渲染输出
```

#### 3.1.2 Paging3 + RemoteMediator

**原理**：Paging3 是 Google 官方分页库，`PagingSource` 负责提供分页数据，`RemoteMediator` 负责协调网络请求与本地缓存的写入。

**在本项目的应用**：
- `Pager(PagingConfig(pageSize=20))` 配置分页参数
- `NewsRemoteMediator` 实现 `initialize()` / `load()` 回调
- `load(LoadType.REFRESH)` 时清空 Room 并重新拉取
- `load(LoadType.APPEND)` 时按 `remote_keys` 继续拉下一页
- `load(LoadType.PREPEND)` 暂不实现（信息流不向前翻页）
- Room 的 `PagingSource` 直接被 `Pager` 消费，**离线天然支持**

**关键设计点**：`initialize()` 返回 `SKIP_INITIAL_REFRESH`，**避免冷启动时清空 Room 缓存**，保证离线可用。

#### 3.1.3 Room 离线缓存

**原理**：Room 是 Google 官方 ORM 库，对 SQLite 做编译期 SQL 校验和协程支持。WAL（Write-Ahead Logging）模式允许读写并发不阻塞。

**在本项目的应用**：
- 3 张表：`feed_items`（列表数据）/ `remote_keys`（分页游标）/ `news_content_cache`（详情页 LLM 解析结果）
- WAL 模式：`setJournalMode(WRITE_AHEAD_LOGGING)`，列表滚动时不影响数据写入
- `channel` 字段建索引，频道切换时查询更快

#### 3.1.4 详情页三级兜底解析

**原理**：爬虫 + 启发式解析 + LLM 结构化输出，构成分级降级链路。

```
卡片点击 → OkHttp GET 源 URL
              ↓ 抓取失败
         提示"内容不可用"
              ↓ 抓取成功
         Jsoup 启发式解析（按 article / h1 / p 标签权重）
              ↓ 解析失败（页面结构特殊）
         Minimax LLM 调用（HTML → JSON 结构化输出）
              ↓ LLM 调用失败（网络 / Key 异常）
         Mock 兜底（合成正文，保证页面永远有内容）
```

每一级都有缓存（Room），二次进入秒开。

#### 3.1.5 Hilt 依赖注入

**原理**：Hilt 是 Google 官方 DI 库，基于 Dagger，编译期生成依赖图。

**在本项目的应用**：
- `NetworkModule` 提供 OkHttp / Retrofit
- `DatabaseModule` 提供 Room
- `DataSourceModule` 提供 Mock / Real 数据源（**一键切换**）
- `RepositoryModule` 提供 Repository 实现
- `AiModule` 提供 MinimaxChatClient

**亮点**：数据源切换时 Repository **零修改**，只需在 Hilt Module 切换绑定。

#### 3.1.6 Compose 性能优化原理

**原理**：Compose 重组（Recomposition）由"参数变化"和"作用域"共同决定。`@Immutable` 告诉编译器"这个类的所有属性都不可变"，编译器可以放心做引用比较跳过重组。`remember` 把计算结果缓存到 Slot Table，跨重组复用。

**在本项目的应用**：
- `FeedCard` 加 `@Immutable`
- `HomeTopBar` / `AppBottomNav` 的 tabs 列表用 `remember` 缓存
- `BottomInfoRow` 用 `remember(commentCount)` 缓存评论数格式化结果
- `LazyColumn items` 显式 `key` 提升 item 复用率
